# Qoder（阿里）：从零讲明白

## 1. 它到底是什么

Qoder 是阿里的 **Agent 优先编程平台**：不只补全下一行，而是你说目标，它规划、改仓库、跑命令、让你审查结果。

形态有好几个外壳，内核尽量同一套：

- **Qoder IDE**：长得像编辑器，但突出 Quest（任务窗）  
- **Qoder CLI**：终端里的编程搭档，思路很像 Claude Code  
- 还有插件 / 账号打通等周边  

口号可以记成官方那句：**Define the goal. Review the result.（定目标，审结果。）**  
人少盯过程，多盯 diff 和是否达标。

## 2. 它想解决什么问题

程序员用普通聊天补全，会卡在：

- 一个需求要改很多文件，聊天框里说不清仓库长什么样  
- 每次新对话都像失忆，架构约定要反复粘贴  
- 想「丢一个任务让它自己跑完」，而不是一句一句喂  

Qoder 的产品句是：把仓库变成 Agent 读得懂的知识，把开发变成 **委派任务 + 审查交付**。

它还往「需求 → 架构 → 编码 → 测试 → 审查 → 提交/PR」整条链上靠。完整 SDLC 是大厂愿景；你从零只要先做「改代码 + 给你看 diff」。

## 3. 设计概念

### 四个齿轮（官方 CLI 也这么拆）

| 齿轮 | 白话 | 没有它会怎样 |
|---|---|---|
| **Agent** | 会想下一步的循环 | 变成一次性作文 |
| **工具** | 读改搜跑、网页 | 模型只能空谈 |
| **权限** | 每次工具：立刻做 / 问你 / 禁止 | 要么不敢干活，要么乱删 |
| **上下文** | 对话 + 项目说明 + 长期记忆 | 每次都像新来的实习生 |

### Quest（任务）

不要当成又一个聊天标签。Quest 是一张工单：

- 有状态：Running / 等你操作 / 完成 / 出错  
- 有工作区（哪个仓库）  
- 结束后有 **审查**：看 diff、拒单个文件、提交、推送  

界面常常是三栏：左边任务列表，中间过程，右边进度 / diff / 知识引用。

两种子模式（创建时选定，中途不要随便切）：

- **Agent**：一个智能体端到端  
- **Experts（专家团）**：多角色并行，适合全栈或疑难

### Repo Wiki / 知识卡片 / Memory

用老奶奶的话说：

- **Repo Wiki**：给仓库自动写说明书（模块怎么连、目录是什么），并尽量跟代码同步。Agent 先读说明书，少把整个仓库塞进窗口。  
- **知识卡片**：从代码和讨论里剪下来的要点，一张一张，比 Wiki 更碎、更好检索。  
- **Memory**：跨对话记住「这个项目测试用 pytest」「不要动某目录」。

项目静态约定还常常放在 `AGENTS.md`、rules 里——相当于墙上贴的员工手册，每次开工都读。

### Plan / Goal / Workflow

同一套循环，换「怎么停、怎么并行」：

- **Plan**：先写出计划给你看，再动手  
- **Goal**：目标一直挂着，自动往下做，直到达标或你暂停  
- **Workflow**：多 Agent 分阶段、可并发  
- **Headless**：给脚本 / CI，没人点按钮时，权限策略必须事先写死  

编辑旧消息会 **回滚工作区** 再到那一句之前——这是「时间旅行」，实现成本高，最小版可以不做，但要知道完整产品为什么要它：否则改历史聊天和磁盘会对不上。

## 4. 系统拆成哪些积木

1. **壳**：IDE 或 CLI。IDE 负责画 Quest 和 diff；CLI 负责在终端打印工具调用。  
2. **Agent 循环**：收请求 → 规划 → 工具 → 观察 → 继续或结束。可用 `--max-turns` 防死循环。  
3. **工具箱**：读、写、编辑、Glob、Grep、Bash、可选网页。MCP / Skills / Subagents 往外扩。  
4. **权限引擎**：每个调用 → allow / ask / deny。Headless 里 `ask` 往往直接当拒绝，避免卡住流水线。  
5. **知识中心**：Wiki 生成器（定时或打开仓库时扫）、记忆存储、规则文件加载器。  
6. **审查与 Git**：diff 视图、拒绝文件、commit、PR。这是「Review the result」的落点。  
7. **可选重型件**：内置浏览器预览前端、Spec 驱动开发面板、云端继续跑。

## 5. 一次 Quest 怎么走

```
你打开 Quest，绑定仓库，说「给登录加上单测」
    → 加载 AGENTS.md、相关 Memory、Wiki 里认证那一章
    → 模型决定：Grep login → Read 测试目录 → 编辑测试文件 → 跑测试
    → 权限：读自动过，写文件可能问你（取决于模式）
    → 测试红了，输出进上下文，再改
    → 状态变成 Ready，右侧出现 diff
    → 你拒绝某个文件或全部接受，再点提交
```

CLI 没有三栏窗，但循环相同：打印步骤，敏感操作在终端问 y/n。

## 6. 从零开发：先做「委派 + 审查」，不要先做 IDE

完整 Qoder 是 IDE + 知识工程 + 多 Agent + 账号云。你从零做 **同类最小系统**。

**第 0 周：带仓库路径的聊天**  
启动时选定一个文件夹。系统提示词写：「你的工作区是这个路径，回答必须基于真实文件。」仍无工具。这只是让你习惯「任务绑仓库」。

**第 1 周：Read + Grep + Glob**  
三个只读工具。能回答「登录逻辑在哪」才进入下一周。搜索用 ripgrep，不要一上来做向量库。

**第 2 周：编辑 + diff 预览**  
只允许补丁（unified diff）或「按行替换」。应用前必须能看 diff、能整单拒绝。**禁止**静默覆盖。

**第 3 周：权限三态**  
配置里写：`read=allow`，`write=ask`，`bash=ask`。终端打印「将执行 xxx，y/n」。Headless 模式把 ask 变 deny。

**第 4 周：任务状态机**  
每个任务：id、仓库、状态、日志。这就是简陋 Quest。还不用 IDE，一个 CLI 或一个窗口列表就够。

**第 5 周：AGENTS.md**  
启动时若根目录有这个文件，整份塞进系统提示（注意长度上限，太长就截章节）。这是 Memory 的静态版。

**第 6 周：跑测试这一类 Bash 白名单**  
允许 `npm test` / `pytest` 等，有超时、有工作目录限制。红了把 stdout/stderr 喂回模型。

**第 7 周：Wiki 雏形**  
定期或手动：对每个目录生成 `wiki/模块.md`（用模型总结该目录 README + 文件名列表，不要每次全仓嵌入）。Agent 先 Read wiki 再搜代码。

**更后才考虑**  
专家团、Quest 三栏 IDE、编辑消息回滚磁盘、自动 PR、浏览器 Agent。那些是产品厚度，不是「目标—工具—审查」这条脊梁。

## 7. 你不能省略的硬决定

- **人审什么**：Qoder 把审查做成一等界面。你若做成「自动写盘再 git push」，性质就变了。  
- **上下文从哪来**：对话会胀。必须有压缩（Compact）或「新开 Quest」。Wiki/Memory 是为了少把仓库原文塞进去。  
- **目录信任**：第一次打开某仓库要询问「允许在这里跑命令吗」。不要对任意路径执行 Bash。  
- **SDLC 边界**：需求、架构、部署可以当提示词阶段，但落地仍是补丁和测试。不要第一天做自动上线。

## 8. 和 MacBuddy

MacBuddy 的 **Code 切片** 应停在：理解仓库、给补丁、你预览、可选本地 git。  
不要去做 Qoder 那种完整 IDE、Repo Wiki 工厂、Quest 看板、专家团编排。

该学的：任务绑工作区、权限三态、`AGENTS.md` 当项目手册、结束时强制看 diff。  
不该学的：和阿里抢「自主开发 IDE」叙事。
