# OpenAI Codex：从零讲明白

## 1. 它到底是什么

Codex 首先不是「又一个聊天窗口」，而是一套 **Agent 发动机（harness）**。  
官方 CLI、终端界面（TUI）、VS Code 插件、后来的 Mac 应用，底层尽量共用同一套循环。

比喻：

- Cursor = 改装好的整辆汽车（驾驶舱就是编辑器）  
- Codex = **发动机 + 标准插座**，你可以接方向盘（TUI）、接大屏（IDE）、接遥控器（云端任务）  

2026 年公开的关键积木叫 **App Server**：一个长期活着的子进程，和外壳用 **JSON-RPC** 说话（一种「双方都能主动提问」的电话协议）。

## 2. 它想解决什么问题

OpenAI 发现：每做一个新界面（终端、编辑器、桌面），如果把「怎么调模型、怎么调工具、怎么等人批准」再写一遍，会分叉、会出 bug。

所以开发思路是：

1. 把循环做成 **Rust 写的核心**（快、内存可控、能沙箱）  
2. 所有 UI 都变成 **客户端**  
3. 客户端只负责显示事件、收集你点的批准，不负责「模型下一秒干什么」  

另外还要：命令行里能用、CI 里能无界面跑、笔记本休眠时云端还能继续。

## 3. 设计概念

### Thread / Turn / Item（线、回合、条目）

用打电话比喻：

- **Thread（会话线）**：你和助手的整段关系，有历史  
- **Turn（一回合）**：你说一句「去修测试」，到助手告一段落  
- **Item（条目）**：这一回合里发生的小事：一段文字、一次工具调用、一次「请你批准删文件」  

客户端画界面时，只是把 Item 一条条画出来。核心不关心按钮长什么样。

### 提交队列 / 事件队列

你点发送 = 往核心丢一个「提交」。  
核心一边干一边往外喷「事件」（开始想了、吐了一个字、要跑命令了、命令结束了）。  
所以界面可以随时取消：再丢一个「取消」提交进去，循环看到就停。

### App Server 反向提问

普通 HTTP 是你问服务器答。  
JSON-RPC 双向意味着：**模型想删文件时，服务器可以反过来问客户端「用户批不批准？」** 然后这回合卡住，直到你点是或否。这是安全设计，不是锦上添花。

### 沙箱

工具不直接在你的电脑上为所欲为。Linux 上常用类似 bubblewrap 的隔离：能碰到的目录、网络被限制。默认更收，比「Agent 直接 rm -rf」安全。

### Worktree

并行多个 Agent 改同一仓库时，每人一份 git 工作树，避免互相踩文件。这是「并行」的工程答案，不是再开一个模型那么简单。

## 4. 系统拆成哪些积木（公开架构）

1. **core**：会话、回合循环、工具路由、配置  
2. **app-server**：JSON-RPC、线程管理器、每个 Thread 一个核心会话  
3. **TUI / exec CLI / IDE 插件 / Mac App**：都是客户端  
4. **tools + MCP**：内置工具 + 外接 MCP 服务器  
5. **落盘**：会话 JSONL（一行一个事件，方便回放）+ SQLite 一类状态  

一次采样（问模型）前后还可能有：钩子（hooks）、上下文太长时的压缩（compaction）、再调工具。

## 5. 一次请求怎么走

```
客户端启动 → 拉起 App Server 子进程，打开标准输入输出管道
你输入任务 → JSON-RPC: 创建 Thread / 提交 Turn
核心组装消息和工具列表 → 调模型流式输出
若有 tool_call → 沙箱执行 → 结果变成事件推给客户端
若需批准 → 服务器发请求给客户端 → 你点按钮 → 回合继续
Turn 结束 → 客户端画「完成」
```

远程模式：App Server 跑在有 GPU 的机器上，你的 TUI 只连过去。这是「发动机靠近算力」的设计。

## 6. 从零开发（最小 Codex 形状）

不要第一天写 Rust。先验证「一个循环、两个进程」。

**第 0 周：单进程 while 循环**  
Python 即可：`messages` 数组，调聊天接口，若返回 tool_calls 就执行，把 role=tool 的消息 append，再调。打印每一步。这就是 Codex 的灵魂，一百行也能看见。

**第 1 周：把循环塞进子进程**  
子进程只打印 JSON 行：`{"type":"token","text":"..."}`、`{"type":"tool","name":"read","path":"..."}`。父进程（你的 UI）只读这些行。这就是简陋 App Server。

**第 2 周：批准**  
遇到 `run_terminal`，子进程发 `{"type":"need_approval","cmd":"..."}`，父进程等你输入 y/n 再写回管道。

**第 3 周：取消**  
用户点停，父进程发 `{"type":"cancel"}`，子进程打断 HTTP 流。

**第 4 周：会话落盘**  
每个事件 append 到 jsonl。刷新页面能重放。DeepSeek Harness 后来把「模型看见的都必须能从日志重建」写成铁律，Codex 的 jsonl 是同一类思想。

**第 5 周：沙箱白名单**  
工作区以外的路径拒绝。没有隔离就不要开放任意 shell。

**更后：Rust、MCP、worktree、云端任务** —— 那是规模，不是灵魂。

## 7. 硬决定

- 核心和 UI 的协议一旦乱改，所有客户端一起炸；要当产品的宪法  
- 默认可不可以不批准就写盘？Codex 倾向可配置、默认更谨慎  
- 无界面 `exec` 模式给 CI：没有人点按钮时，批准策略必须事先写死  

## 8. 和 MacBuddy

MacBuddy 的 LLM / Work / Code sidecar + Unix socket，已经是「发动机在隔壁进程」。向 Codex 学的是：把事件协议写清楚（token / tool / approval / done / error），SwiftUI 只投影，不要在 View 里写 Agent 状态机。
